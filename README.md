# Analytics Portal

Аналитический портал для интернет-продаж и управления промо: Go/Gin API, React/Vite UI, Microsoft SQL Server и Python-скрипты синхронизации.

## Быстрый запуск через Docker

Требования: Docker Desktop и Docker Compose.

1. Создайте локальный файл окружения:

   ```bash
   cp .env.example .env
   ```

2. Замените `SA_PASSWORD`, `JWT_SECRET` и `BOOTSTRAP_PASSWORD` уникальными значениями. Реальные значения не должны попадать в Git.

3. Соберите и запустите весь стек:

   ```bash
   make up
   ```

   Backend дождётся SQL Server, создаст `DB_NAME`, если базы ещё нет, и применит все Goose-миграции.

4. Один раз создайте первого пользователя:

   ```bash
   make bootstrap-user
   ```

   Команда создаёт только нового пользователя. Существующий пароль или роль она не изменяет.

5. При необходимости добавьте демонстрационные данные (только не для `APP_ENV=production`):

   ```bash
   make seed-dev
   ```

После запуска:

- интерфейс: <http://localhost:5173>;
- API: <http://localhost:8080>;
- liveness: <http://localhost:8080/health>;
- readiness БД: <http://localhost:8080/ready>.

`make down` останавливает контейнеры, но сохраняет данные. Для полностью чистой локальной базы нужно явно удалить volume командой `docker compose down -v`; это необратимо для данных Docker-volume.

## Изолированная демонстрационная БД

`docker-compose.demo.yml` поднимает отдельный контур `my_project_demo` и не
монтирует рабочий `my_project_mssql_data_volume`. По умолчанию используются:

- SQL Server: `127.0.0.1:1434`, том `my_project_demo_mssql_data_volume`;
- база: `local_project_demo_db`;
- backend: <http://localhost:8081>;
- frontend: <http://localhost:5174>.

Создание схемы и первая загрузка промо-среза:

```bash
make demo-db-init
docker compose up -d mssql_db
make demo-db-load
docker compose stop mssql_db
```

На время загрузки нужен только исходный SQL Server; рабочие backend/frontend
можно не запускать. После контрольной сверки исходный SQL-контейнер можно снова
остановить, как показано выше.

Загрузчик читает рабочую БД только через `SELECT`. В demo-БД он переносит
активный промо-срез (soft-deleted строки не копируются) и:

- стабильно заменяет сети, КАМ, бренды и SKU во всех промо-таблицах;
- объединяет варианты КАМ с переставленными именем и фамилией;
- сохраняет годы, месяцы, механики, каналы и структуру `NULL`;
- меняет исходные числа ограниченными детерминированными коэффициентами;
- пересчитывает производные показатели по формулам приложения;
- заменяет условия, комментарии, согласования и историю синтетическим текстом;
- не переносит пользователей, пароли, refresh-сессии и журналы дедупликации.

Повторная загрузка требует отдельной защитной команды и очищает все
демонстрационные данные demo-БД — промо, интернет-продажи и реестр сетей.
Загрузчики выстроены в цепочку, поэтому после сброса промо нужно повторить
и остальные шаги:

```bash
make demo-db-reset
make demo-ecom-load
make demo-registry-load
```

### Демонстрационные интернет-продажи

Интернет-продажи не переносятся из рабочей БД, а генерируются заново — исходный
SQL Server для этого не нужен:

```bash
make demo-ecom-load
```

Загрузчик берёт сети, бренды и SKU из уже загруженных демо-справочников, поэтому
экраны промо и интернет-продаж показывают одни и те же сущности. Масштаб пары
«сеть × SKU» отсчитывается от пикового месяца её промо, а цена `OLAP SS` — от
`olap_price` демо-промо того же года, так что цены контракта в реестре сетей
сходятся с промо (проверка падает при расхождении больше 15%).

Динамика не выдумывается: погодовой уровень каждой сети и каждого SKU берётся
из демо-промо, которое пришло из рабочей БД и уже несёт реальную картину. Сеть,
терявшая объём в промо, теряет его и в интернет-продажах — иначе две витрины
рассказывали бы про одни и те же сети разное. Промо-ряд при этом не копируется
один в один: он отражает промо-активность, и сеть, свернувшая акции, даёт там
падение в разы. Индекс считается относительно рынка, сжимается корнем и
ограничивается по шагу и по уровню, так что знак динамики сохраняется, а
масштаб остаётся правдоподобным для полных продаж.

Ряды строятся как гладкие функции номера месяца — опорный объём × сезонность ×
уровень × медленная волна, — поэтому соседние месяцы отличаются на единицы
процентов. Показатели «без Ecom» получаются вычитанием онлайновой части из
общей, а не отдельной генерацией: доля Ecom по построению лежит между 0 и 100%,
а «wo Ecom» не может превысить полный объём. Справочник `dimEcomSegment.csv`
переносится без изменений: сегменты `OLAP SS`, `OLAP NW` и `… wo Ecom`
захардкожены в backend и frontend, а разбивка по площадкам — сама суть витрины.

Повторная генерация требует защитной фразы и очищает только интернет-продажи:

```bash
make demo-ecom-reset
```

Горизонт по умолчанию — с первого года демо-промо по декабрь последнего полного
года промо; отсечку задаёт `--last-period YYYY-MM`. Год обрывать не стоит:
дашборд сравнивает год к году календарно, без выравнивания по месяцам, и на
неполном последнем году вся динамика ушла бы в минус из-за длины периода, а не
из-за данных. Значения зависят только от абсолютного номера месяца, поэтому
повторный запуск с более поздней отсечкой оставляет ранее сгенерированные
месяцы прежними.

### Демонстрационный реестр сетей

Реестр наполняется третьим шагом, после интернет-продаж:

```bash
make demo-registry-load
```

Карточки сетей берутся из демо-справочника: имя, КАМ и тип — те же, что в промо,
поэтому фильтр списка по КАМ работает на реальном распределении. Факт отгрузок
не выдумывается, а собирается из сегмента `OLAP NW` интернет-продаж — того
самого, который и означает отгрузки. Из-за этого реестр, промо и продажи
показывают одни и те же сети с одной и той же динамикой.

План считается от факта, а не наоборот: квартальный план получается делением
факта на коэффициент выполнения, поэтому часть кварталов перевыполнена, часть
провалена, и форма «план / факт» не выглядит подогнанной под ответ. Проверка
падает, если перевес оказался односторонним хотя бы на одном закрытом году.

Годы определяются по данным продаж: факт грузится за последний год и
предыдущий, планы — на оба этих года и на следующий. Каждый год с фактом
считает план от своего же факта, поэтому сравнение «план / факт» открывается на
любом из них. Последний плановый год остаётся без факта и показывает работу с
планом до появления отгрузок, а системный прогноз на него считается по факту
прошлого года.

Цены контракта отдельно не грузятся: приложение подставляет их из среза
`OLAP SS` за последний доступный месяц 2026 года.

Повторное наполнение требует защитной фразы:

```bash
make demo-registry-reset
```

### Учётные записи демо-контура

Роли приложения: `admin`, `kam` (ведёт сети и промо), `agreement1` и
`agreement2` (две ступени согласования). Роль задаётся при заведении и в
интерфейсе не меняется.

По учётной записи на каждого КАМа справочника заводит отдельная команда.
Пароли она генерирует на машине запускающего и печатает один раз — сохраните
их сразу, повторно узнать пароль нельзя, можно только завести пользователя
заново под другим именем:

```bash
make demo-kam-users-preview   # какие логины будут заведены, без паролей
make demo-kam-users           # завести и показать пароли
```

Логин собирается транслитерацией имени: «Ершов Максим» → `kam.ershov.maksim`.
Уже существующие пользователи пропускаются, пароль им не меняется.

### Видимость промо

Учётная запись КАМа закрепляется за именем из справочника (`tbl_Users.kam`) —
без этой связи вошедшего КАМа не с чем сопоставить, потому что логин и имя КАМа
в промо живут отдельно. Закрепление проставляет `make demo-kam-users`; починить
его у уже заведённых учёток можно, не трогая пароли:

```bash
python3 sync_script/create_demo_kam_users.py --link-only
```

Область видимости промо складывается из собственного закрепления и КАМов, за
которых пользователь согласует. Поэтому рядовой КАМ видит только свой портфель,
руководитель — свой и портфели подчинённых, а администратор не ограничен вовсе.
Ограничение применяется на сервере во всех читающих путях сразу: справочники
фильтров, строки, дашборд, выгрузка в Excel и открытие промо по ссылке. Область
входит и в ключ кэша справочников, иначе срез одного КАМа достался бы другому.

Та же область действует и на записи: КАМ заводит и правит промо своего портфеля
(руководитель — ещё и портфели подчинённых), а чужое промо получает отказ. КАМ
правки берётся из базы, а не из тела запроса, поэтому подменой поля чужую запись
не открыть; перенос промо на КАМа вне области закрыт так же, как правка чужого.

Учётная запись с ролью `kam` без закрепления и без области доступа не получает
вовсе: и промо, и реестр сетей отвечают ей `403` с текстом «учётная запись не
привязана к КАМу». Пустая область у этой роли означает пропущенный шаг при
заведении пользователя, а не разрешение видеть весь портфель компании, поэтому
режим отказа здесь fail-closed, а причина называется прямо — иначе КАМ видел бы
пустую таблицу и считал, что промо просто нет. Чинится закреплением:

```bash
python3 sync_script/create_demo_kam_users.py --link-only
```

Администратора и унаследованных согласующих (`agreement1`, `agreement2`) это не
затрагивает: у них пустая область по-прежнему означает отсутствие ограничения —
до появления этой связи промо видели все, и молча спрятать их у уже работающей
учётной записи хуже, чем оставить прежнее поведение.

### Потолок выборки промо

Таблица «Анализ промо» листается страницами на сервере: поиск и сортировка тоже
серверные, потому что в браузере лежит только текущая страница.

Целиком (`all=true`) выборку запрашивают выгрузки, и у неё есть потолок —
`PROMO_MAX_ROWS`, по умолчанию 50 000 строк. Сверх него сервер отвечает 413 с
числом строк и лимитом и предлагает уточнить фильтры или выгрузить в Excel:
эта выгрузка идёт потоком из курсора БД и в память вкладки не попадает.
Потолок ниже, чем `SALES_EXPORT_MAX_ROWS` у продаж (200 000), именно поэтому:
там строки уходят потоком, здесь — в память браузера.

### Область согласования

По умолчанию согласующий видит очередь по всем КАМам. Чтобы ограничить его
своими подопечными, заводится область согласования — строки вида «промо этого
КАМа на этой ступени согласует этот пользователь». Отсутствие строк означает
прежнее поведение без ограничения, поэтому уже заведённых согласующих это не
затрагивает.

Ограничение применяется на сервере и к чтению, и к согласованию: фильтр по КАМу
приходит из запроса и потому доверия не заслуживает, а КАМ промо перед записью
читается из базы. Вне области недоступны даже имена КАМов в фильтре.

Роль `kam` тоже допускается к согласованию, но только при наличии области:
ступень берётся из закрепления, а не из роли. Свои промо в область не входят,
поэтому руководитель их не согласует — для них достаточно первого согласующего.

Демонстрационная связка (старший КАМ и четыре подчинённых) ставится одной
командой после того, как заведены учётные записи КАМов:

```bash
make demo-approval-scope
```

Произвольная связка и снятие области:

```bash
python3 sync_script/set_demo_approval_scope.py --user <логин> --stage 2 --kam "<КАМ>"
python3 sync_script/set_demo_approval_scope.py --user <логин> --clear
```

Согласующего на все сети заводят штатной командой — задайте в локальном `.env`
`DEMO_BOOTSTRAP_USERNAME`, `DEMO_BOOTSTRAP_PASSWORD` и
`DEMO_BOOTSTRAP_ROLE=agreement1` (или `agreement2`) и выполните:

```bash
make demo-bootstrap-user
make demo-up
```

Остановка demo-контура сохраняет его отдельный том:

```bash
make demo-down
```

## Локальный запуск без Docker

Нужны Go 1.25+, Node.js 24+, SQL Server 2022 и ODBC Driver 17/18 для Python-скриптов.

Backend:

```bash
cp backend/.env.example backend/.env
cd backend
go run .
```

При `DB_AUTO_CREATE=true` пользователь SQL Server должен иметь право `CREATE DATABASE`. В production рекомендуется заранее создать базу отдельной административной учётной записью и установить `DB_AUTO_CREATE=false`.

Создание первого пользователя выполняется отдельно после применения миграций:

```bash
cd backend
go run ./cmd/bootstrap_user
```

Параметры берутся из `BOOTSTRAP_USERNAME`, `BOOTSTRAP_PASSWORD` и `BOOTSTRAP_ROLE` в окружении. Допустимые роли: `admin`, `agreement1`, `agreement2`.

Frontend:

```bash
cp frontend/.env.example frontend/.env
cd frontend
npm ci
npm run dev
```

## Схема базы

Goose-миграции встроены в backend-бинарник и применяются при запуске. Чистая установка создаёт:

- `tbl_PromoActivities`, `tbl_PromoComments`, `tbl_AuditLog`;
- `tbl_EcomSalesConsolidated`, `tbl_EcomSalesNormalized`;
- `tbl_ChannelSegmentMapping`, `tbl_SKUMapping`, `tbl_KAMNetworkMapping`, `tbl_MechanicsChannelMapping`, `tbl_NetworkGeoMapping`;
- `tbl_Networks`, `tbl_NetworkPeriods`, `tbl_NetworkPlans`, `tbl_NetworkComments`;
- `tbl_Users`, `tbl_RefreshSessions`.

Основные проверки месяцев, кварталов, ролей и статусов согласования закреплены ограничениями SQL Server. Для часто используемых фильтров и связей созданы индексы.

Dev-seed находится в `backend/cmd/seed_dev/dev.sql`, не содержит пользователей и повторно применяется безопасно.

## Выгрузка интернет-продаж

`GET /api/data?all=true` отдаёт выборку целиком, построчно, не собирая её в памяти сервера. Размер ограничен переменной `SALES_EXPORT_MAX_ROWS` (по умолчанию 200000): при превышении запрос отклоняется с кодом `413` и текстом, сколько строк запрошено и каков лимит. Для больших объёмов используйте `GET /api/data/export-xlsx` — этот эндпоинт формирует файл потоком и лимитом не ограничен.

### Фоновая выгрузка

`POST /api/data/export-jobs` готовит файл в фоне, `GET /api/data/export-jobs/:id`
отдаёт статус, `.../download` — сам файл. Объём ограничен
`SALES_BACKGROUND_EXPORT_MAX_ROWS` (по умолчанию 1 000 000).

Готовые файлы лежат в `SALES_EXPORT_DIR` (по умолчанию — подкаталог
`analytics-portal-exports` во временной директории) и живут не дольше часа.

**Состояние заданий хранится в памяти процесса.** После перезапуска реестр
пуст, и опрос статуса вернёт `404` — выгрузку нужно запустить заново; файлы
предыдущего запуска удаляются при старте, иначе их не убрал бы никто: чистка
по расписанию обходит именно реестр заданий. Задание, не отчитавшееся за
30 минут, помечается провалившимся: горутина, которая перевела бы его в
`failed`, уже не отчитается. Если выгрузки должны переживать перезапуск или
работать на нескольких репликах, состояние нужно вынести в БД, а каталог — на
общий том.

## Синхронизация данных

```bash
cp sync_script/.env.example sync_script/.env
python3 -m venv sync_script/.venv
source sync_script/.venv/bin/activate
pip install -r sync_script/requirements.txt
python sync_script/sync_data.py
```

`sync_data.py` переносит интернет-продажи из OLAP и обновляет нормализованную таблицу.

Импорт промо выполняется через временную staging-таблицу и фиксируется одной транзакцией:

```bash
# Сначала проверить структуру, значения и дубли без подключения к БД
python sync_script/import_promo.py /path/to/promo.xlsx --dry-run

# Безопасный режим: добавить новые и обновить существующие записи
python sync_script/import_promo.py /path/to/promo.xlsx
```

По умолчанию записи, отсутствующие в Excel, не изменяются. Только если файл является полным снимком всего реестра, можно явно включить soft-delete отсутствующих активных записей:

```bash
python sync_script/import_promo.py /path/to/promo.xlsx --full-snapshot
```

### Помесячный факт реестра сетей

План КАМ задаёт по кварталам, прогноз — по месяцам, а факт приходит выгрузкой отгрузок
и в интерфейсе доступен только для чтения:

```bash
# Проверить файл и сопоставление сетей, ничего не записывая
python sync_script/import_network_facts.py /path/to/facts.xlsx --dry-run

# Загрузить
python sync_script/import_network_facts.py /path/to/facts.xlsx
```

Ожидаемые колонки (Excel или CSV; регистр и пунктуация в заголовках не важны):

| Колонка | Обязательна | Комментарий |
| --- | --- | --- |
| `Сеть` | да | сопоставляется с названием в реестре |
| `Бренд` | да | `brand_as` строки плана |
| `SKU` | нет | если пусто, строка считается итогом бренда |
| `Год`, `Месяц` | да | месяц 1–12 |
| `Факт, руб` | одна из трёх | фактический объём |
| `Факт, уп` | одна из трёх | фактические упаковки |
| `Факт инвестиций, руб` | одна из трёх | фактические инвестиции |

Файл проверяется целиком до записи: пустые ключи, нечисловые и отрицательные значения, неверный месяц и дубли строк перечисляются одним списком. Загрузка и квартальный roll-up выполняются одной транзакцией. Сети, которых нет в реестре, останавливают загрузку и выводятся с подсказкой похожих названий:

```
Не найдено сетей в реестре: 2
  «Магнит ММ» — похоже на: Магнит
  «Ашан» — похожих в реестре нет
```

Их либо переименовывают в файле, либо заводят в реестре, либо пропускают явным флагом `--allow-unknown-networks`.

Пустая ячейка означает «значение не пришло» и уже загруженное не затирает, поэтому объём и инвестиции можно грузить разными файлами. Бренд, которого нет в плане, добавляется новой строкой вне валового объёма: факт по незапланированному бренду не теряется.

### Импорт промо

Экспорт портала содержит колонку `ID промо`. Для существующих записей импорт использует этот ID и поэтому корректно различает несколько промо с одинаковыми сетью, SKU, месяцем и механикой. Для строк без ID старый составной ключ используется только при однозначном совпадении; неоднозначный импорт блокируется. Поля согласования управляются приложением и из Excel не перезаписываются.

Перед записью импорт отклоняет пустые ключи, повторяющиеся ID, неверные числа и даты, несовместимую схему БД и неоднозначные совпадения. При любой ошибке вся транзакция откатывается.

### Аудит и очистка точных дублей промо

Сначала сформируйте JSON-план только чтением:

```bash
python sync_script/dedupe_promo.py report --output /secure/path/promo-dedup-plan.json
```

План разделяет группы на `exact_duplicate`, `approval_conflict` и `data_conflict`. Автоматически применяются только полностью идентичные записи; конфликтные промо не изменяются.

```bash
python sync_script/dedupe_promo.py apply \
  --plan /secure/path/promo-dedup-plan.json \
  --confirm APPLY_SAFE_EXACT_DUPLICATES
```

Комментарии и аудит переносятся на выбранную основную запись, а лишние строки только помечаются удалёнными. Все перемещения сохраняются в таблицах журнала миграции `007`, поэтому запуск можно полностью откатить по напечатанному `run_id`:

```bash
python sync_script/dedupe_promo.py rollback \
  --run-id 00000000-0000-0000-0000-000000000000 \
  --confirm ROLLBACK_SAFE_DEDUP
```


Браузерные smoke-тесты запускаются отдельно:

## Production

Production override отключает автоматическое создание БД, требует явные HTTPS-адреса и скрывает порт SQL Server от хоста:

```bash
docker compose -f docker-compose.yml -f docker-compose.production.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.production.yml up -d --build
```

Пример несекретных параметров находится в `ops/production.env.example`, эксплуатационный чек-лист — в `ops/README.md`. Пароли и JWT-секрет передаются только через защищённое окружение или secret manager.

### Заголовки безопасности фронтенда

`frontend/security-headers.conf` отдаётся со всей статикой: CSP, `X-Content-Type-Options`,
`X-Frame-Options`, `Referrer-Policy`; версия nginx скрыта (`server_tokens off`). Файл
включается в каждый `location` — nginx отменяет наследование `add_header`, как только в
блоке появляется свой, а заголовки кеширования есть почти везде.

Главное здесь — CSP: access-токен хранится в `localStorage`, поэтому любая XSS означала бы
угон сессии. Разрешено ровно то, что приложение грузит: Google Fonts для Inter,
`'unsafe-inline'` для стилей (emotion вставляет `<style>` на лету) и `connect-src` до
backend.

**Адрес backend в `connect-src` подставляется на сборке образа из того же `VITE_API_BASE`,
что вшивается в бандл** (`frontend/Dockerfile`). Меняя адрес API, пересобирайте фронтенд —
иначе CSP заблокирует первый же запрос:

```bash
docker compose -f docker-compose.yml -f docker-compose.production.yml up -d --build frontend
```
