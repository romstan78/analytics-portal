# План: PDF- и PowerPoint-выгрузка аналитики

## Назначение документа

Этот документ задаёт стартовый план для новой задачи: добавить в Analytics Portal
выгрузку выбранных пользователем данных, графиков и таблиц в PDF и PowerPoint.
Это **план**, а не разрешение на изменение схемы БД, зависимостей, Docker-контура,
миграций или исходного кода.

## Цель

Пользователь формирует отчёт по выбранным фильтрам и получает:

- PDF для рассылки и фиксации результата;
- PPTX для презентации в корпоративном шаблоне.

Первый сценарий — витрина «Реестр сетей». Пользователь выбирает год, кварталы,
КАМов, сети, единицу измерения, набор блоков и их порядок. Позже тот же механизм
должен расширяться на промо и интернет-продажи.

## Границы MVP

### Входит

- Один раздел портала: витрина реестра сетей.
- Форматы PDF и PPTX.
- Фильтры — ровно те, что есть у витрины (`NetworkDashboardFilter`): год,
  кварталы, КАМы, сети. КАМ только в пределах серверной области доступа
  пользователя. Фильтра по брендам у витрины нет, и в MVP он не добавляется:
  сузить агрегацию по бренду — значит менять семантику валового пула и
  `UndistributedRub`; бренды в отчёте показываются блоком `brand-top`.
- Единица измерения — рубли или упаковки — параметр отчёта: витрина
  переключается между ними целиком, и отчёт наследует выбранную.
- Фиксированный каталог блоков, из которого пользователь составляет отчёт.
- Изменение порядка блоков.
- Фоновая подготовка файла, опрос статуса и скачивание владельцем задачи.
- Временное хранение файлов и автоматическая очистка.
- Параметры выборки, автор и дата формирования в документе.

### Не входит в MVP

- Свободный редактор слайдов и перетаскивание объектов по холсту.
- Ручное редактирование чисел в отчёте.
- Передача в API HTML, скриншотов или рассчитанных в браузере значений.
- Нативно редактируемые диаграммы PowerPoint.
- Запуск по расписанию и рассылка по электронной почте.
- Выгрузка из промо и интернет-продаж.
- Фильтр по брендам (см. выше).

## Принципы

1. **Сервер владеет цифрами.** В файл попадают данные, собранные сервером по
   снимку фильтров, а не DOM текущего браузерного экрана.
2. **Авторизация применяется повторно.** Все ограничения области видимости КАМ
   действуют при создании отчёта, подготовке файла и скачивании.
3. **Один снимок на задачу.** После создания задания фильтры, формат и состав
   блоков неизменны; файл воспроизводим и объясним.
4. **Финансовые базы не смешиваются.** GTN, OPEX реестра, promo OPEX и
   альтернативные базы продаж являются разными метриками, имеют отдельные подписи
   и не суммируются без явного правила.
5. **PPTX выглядит стабильно.** В MVP графики и сложные таблицы идут как
   качественные статические элементы в шаблоне. Заголовки, подписи и примечания
   могут оставаться редактируемыми.
6. **Файлы не вечны.** Хранение, очистка и доступ повторяют безопасную модель
   крупных Excel-выгрузок.

## Состав блоков первой версии

Каждый выбранный блок обычно соответствует одному слайду PPTX и одной странице
или секции PDF. Каждый блок читает конкретные поля `NetworkDashboardResponse`
(`models/network_dashboard.go`) — своих чисел у блока нет.

| Код блока | Содержание | Источник в ответе витрины | Ограничение |
| --- | --- | --- | --- |
| `cover` | Заголовок, период, фильтры, автор, дата | метаданные снимка | всегда первый |
| `summary-kpi` | Объём: план, факт, EAC, выполнение, разрыв, YoY | `Summary` | в выбранной единице; готовность данных в подписи |
| `period-trend` | Динамика по кварталам или месяцам | `Quarters` / `Months` | одна выбранная детализация |
| `plan-fact-eac` | Сравнение план, факт, EAC по кварталам | `Quarters` | факт показан с покрытием, не нулём |
| `network-top` | Топ сетей | `Networks` | 10 или 20 строк |
| `brand-top` | Топ брендов | `Brands` | 10 или 20 строк; `InGross` и `UndistributedRub` в подписи |
| `kam-top` | Разрез по КАМам | `KAMs` | только для ролей без закрепления |
| `gtn` | Инвестиции реестра (GTN): план, факт, EAC, отклонение | `Summary.*InvestmentsRub*`, `Quarters` | отдельно от OPEX и от промо; база НДС указана |
| `registry-opex` | Бюджет OPEX реестра | `Summary.RegistryOpexBudgetRub*` | одно число: пары план/факт у бюджета нет по построению |
| `promo-investments` | Инвестиции промо по типу GTN/OPEX | `Summary.PromoInvestments*`, `PromoCount` | не суммируются с инвестициями реестра |
| `network-quarters` | Таблица «сеть × квартал» | `NetworkQuarters` | лимит строк и перенос страниц |
| `methodology` | Методика, источники, оговорки | — | всегда последним при включении |

Блоки одиночной сети — `BrandQuarters`, `BrandMonths`, `SKUs`,
`AnnualInvestmentCumulative` — сервер заполняет только когда в области ровно одна
сеть. В MVP они не входят; при добавлении у блока появляется признак «доступен при
одной сети», и конструктор скрывает его на портфеле.

Финальный перечень и порядок по умолчанию согласовать с пользователями до начала
разработки.

## Пользовательский сценарий

1. Пользователь открывает витрину реестра и нажимает «Экспорт отчёта».
2. Форма подставляет текущие фильтры витрины.
3. Пользователь при необходимости меняет год, кварталы, КАМов, сети и единицу
   измерения в доступных ему пределах.
4. Пользователь отмечает блоки, задаёт порядок, лимит строк таблиц и формат:
   PDF, PPTX или оба.
5. Интерфейс показывает текстовый предпросмотр: будущие названия страниц/слайдов
   и параметры отчёта.
6. Пользователь запускает подготовку.
7. Интерфейс опрашивает состояние фоновой задачи и показывает ссылку на каждый
   готовый файл.

## Целевая архитектура

```text
React-конструктор
  → POST /api/reports
  → ReportRequest
  → сервис ReportSnapshot
  → фоновый ReportJob
  → PDF renderer / PPTX renderer
  → временное файловое хранилище
  → GET статуса и защищённое скачивание
```

### Снимок данных

`ReportSnapshot` — серверная структура, из которой строятся оба формата. Это
**обёртка над готовым `NetworkDashboardResponse`**, который возвращает
`services.BuildNetworkDashboard`: агрегаты, квартальный и месячный ряды, разрезы
по сетям, брендам и КАМам там уже есть, и они по построению сходятся с витриной.
Выделять из сервиса «общую агрегацию» не нужно — сервис не трогается.

Снимок добавляет к ответу витрины только метаданные:

- параметры фильтра и отображаемые названия выбранных объектов;
- владелец задания, время создания и версия шаблона;
- набор выбранных блоков, их порядок, единица измерения, лимиты строк;
- методические подписи: база НДС, gross/net, оговорки.

Отсутствие факта в ответе витрины выражено не `nil` по метрике, а готовностью
данных: `ClosedCells`, `ClosedCellsWithFact`, `FactCoveragePct`,
`OpenCellsWithoutForecast`; `nil` есть только у прошлого года и процентов.
Отчёт показывает эти счётчики рядом с фактом и EAC так же, как витрина, — а
не выдумывает своё представление пустоты.

Дублировать финансовые формулы в renderer или frontend нельзя.

### Фоновые задания

Модель фоновой Excel-выгрузки (`handlers/sales_export_jobs.go`,
`tbl_SalesExportJobs`, миграция 028) служит ориентиром и копируется как есть:
задание выполняется горутиной в том же процессе, файл лежит в
`os.TempDir()/analytics-portal-exports`, TTL один час, зависшие задания
помечаются по `StuckAfter`, при старте удаляются файлы-сироты, паника renderer
переводит задание в `failed`. Приложение работает в одной реплике — общий том и
внешняя очередь не нужны.

Таблица Excel-выгрузок специфична (`total_rows`, нет запроса и формата), поэтому
для отчётов потребуется новая миграция — следующий номер `035` — и отдельная
таблица, например `tbl_ReportJobs`.

Минимальные поля:

| Поле | Назначение |
| --- | --- |
| `id` | UUID задания |
| `owner_name` | владелец, которому доступно скачивание |
| `status` | `queued`, `running`, `ready`, `failed` |
| `request_json` | снимок запроса и состава отчёта |
| `format` | `pdf` или `pptx`; два файла можно хранить как две задачи |
| `file_name`, `file_path` | параметры готового файла |
| `error_text` | безопасное сообщение об ошибке |
| `created_at`, `completed_at` | жизненный цикл и очистка |

Решение: отдельная задача на каждый формат, но одна общая операция в UI.

Рендер тяжелее потоковой Excel-выгрузки, поэтому нужен лимит одновременных
заданий: не больше одного активного (`queued`/`running`) задания на
пользователя и общий потолок на процесс; сверх — `429`.

### API-эскиз

Названия маршрутов уточнить во время реализации; контракт должен жить в Go-моделях
и после изменения пройти `make types`.

```text
POST /api/reports
  request: filters, selectedBlocks, format(s), table limits, title
  response: jobs[]

GET /api/reports/:id
  response: status, safe error, file name, completion time

GET /api/reports/:id/download
  response: PDF or PPTX only for job owner
```

## Рендеринг

### PDF

- Отдельный печатный HTML/SVG-макет, не интерактивная страница портала.
- Графики в SVG, чтобы подписи и линии не теряли качество при масштабировании.
- Альбомный или книжный формат фиксируется на уровне шаблона.
- Таблицы с большим числом строк переносятся на следующие страницы.

### PPTX

- Используется согласованный корпоративный `.pptx`-шаблон.
- Каждый блок знает собственную область слайда и правила переполнения.
- Графики встраиваются растром высокой чёткости (PNG, 2×): библиотеки PPTX не
  вставляют SVG напрямую, а «нативная» диаграмма PowerPoint вне MVP.
- Текстовые примечания, заголовки и служебные поля остаются текстом PPTX.

### Среда, в которой это должно работать

Бэкенд — статический Go-бинарник (`CGO_ENABLED=0`) в образе `alpine:3.22` без
шрифтов и без браузера. Отсюда ограничения, которые план обязан учитывать:

- шрифты с кириллицей встраиваются в артефакт (`go:embed`, как миграции) или
  ставятся в образ — на системные рассчитывать нельзя;
- headless Chromium для PDF означает +300–400 МБ к образу и смену
  Docker-конфигурации — только с разрешения и только если чистые библиотеки
  не справятся;
- зрелой Go-библиотеки для PPTX нет (`unioffice` — коммерческая), поэтому у
  спайка два кандидата разной природы:
  - **Go-native**: PDF через `go-pdf/fpdf` (fork gofpdf, MIT) с встроенным TTF,
    графики через `go-chart` в PNG; PPTX — сборка OOXML вручную из шаблона
    (копирование слайда, замена текста, вставка картинки);
  - **Python-воркер**: `python-pptx` + `reportlab` + `matplotlib` отдельным
    сервисом в `docker-compose` — Python в проекте уже есть (`sync_script`), но
    это новый контейнер, очередь и контракт между сервисами.

Выбор между ними — главный результат спайка, а не деталь реализации.

### Технический спайк до выбора библиотеки

До основной реализации выполнить небольшой изолированный спайк — вне репозитория
проекта, со своими зависимостями. Он должен создать один PDF и один PPTX с
кириллицей, графиком, таблицей из 20 строк и шаблоном (пока корпоративного нет —
пустой с теми же макетами). Проверить:

- работу в целевом Docker-образе (alpine, без системных шрифтов);
- отсутствие обрезания текста;
- корректность шрифтов и кириллицы;
- открытие в Microsoft PowerPoint;
- возможность визуальной проверки PDF;
- лицензию и обслуживаемость выбранного инструмента.

Только после этого добавлять библиотеку, runtime или менять Docker-конфигурацию.

### Результаты спайка (16.09.2026)

Обе ветки собрали одинаковый набор: титул, KPI-таблица, график план/факт/EAC,
таблица 20 сетей с длинными названиями, кириллица, «₽», отрицательное число с
копейками. Шрифт — DejaVu Sans (свободная лицензия), файлом рядом с бинарником;
в реализации уходит в `go:embed`. Шаблон PPTX — пустой 16:9 (корпоративного ещё
нет). Файлы: `report.pdf`, `report.pptx` в каждой ветке.

| | Go-native | Python-воркер |
| --- | --- | --- |
| PDF | `go-pdf/fpdf` v0.9 (MIT). Кириллица и ₽ через `AddUTF8Font`. Высоту строк с переносом и разрыв страницы таблица считает **сама, руками** (~30 строк кода) | `reportlab` 5.0 (BSD). `Table(repeatRows=1)` переносит страницы и повторяет шапку сам |
| График | `go-chart` v2.1 (MIT): шрифт подменяется, но одна серия на диаграмму — группировка план/факт/EAC только подписями, легенды нет, ось Y шумная. `gonum/plot` (сгруппированные столбцы, легенда) не проверен — proxy.golang.org был недоступен | `matplotlib` 3.11: сгруппированные столбцы, легенда, PNG 200 dpi и SVG |
| PPTX | Библиотеки нет. Ручная сборка OOXML поверх шаблона: копия zip + слайды (текст, таблица, картинка) + патч `[Content_Types].xml`, `presentation.xml`, его rels. ~150 строк. `python-pptx` открывает результат: 3 слайда, таблицы 10×2 и 21×7, PNG | `python-pptx` 1.0 (MIT) |
| Docker | `golang:1.25-alpine` → `alpine:3.22`, `CGO_ENABLED=0`, как в проекте. Образ **18,8 МБ**, рендер < 1 с | `python:3.12-slim` + pip. Образ **494 МБ**, рендер ~2 с (без прогрева кэша шрифтов ~20 с) |
| Интеграция | В процессе, горутиной — один в один с Excel-выгрузкой | Новый сервис в compose, очередь/HTTP между сервисами, статус задания в двух местах |
| Не проверено | Открытие в Microsoft PowerPoint — на машине разработки его нет; PDF просмотрен визуально | то же |

**Решение: Go-native.** Он вписывается в существующую модель фоновых заданий
без второго runtime и без изменения `docker-compose`; цена — свой слой таблиц
для fpdf и свой минимальный писатель OOXML, оба уже написаны в спайке и
проверены загрузкой в `python-pptx`. Открытые вопросы до этапа 2:

1. Открыть оба `report.pptx` в Microsoft PowerPoint — обязательное условие
   принятия ручного OOXML.
2. Проверить `gonum/plot` для графиков, когда появится сеть; если не подойдёт —
   собственный SVG→PNG не делать, а принять ограничения `go-chart` для MVP.
3. Получить корпоративный шаблон: писатель OOXML ищет макет «Blank» по имени в
   `slideLayouts`, а не по номеру.

  два воркера, recover от паники, лимит два активных задания на пользователя
  (`429`). Снимок читается один раз в обработчике, оба формата собираются из
  него. Роуты: `GET /api/reports/blocks`, `POST /api/reports`,
  `GET /api/reports/:id`, `GET /api/reports/:id/download`.
- Тесты `handlers/reports_test.go`: успех с файлом, ошибка рендера без
  сироты, паника → `failed`, имя файла.

### Этап 4. PDF и PPTX — выполнен 16.09.2026 (до этапа 3: рендер не зависит от заданий)

Пакет `backend/reports`, зависит только от `models`:

- `pages.go` — страничная модель: блок один раз превращается в заголовок,
  KPI, график, таблицу и примечания; оба формата раскладывают одно и то же.
- `chart.go` — `gonum/plot`, сгруппированные столбцы, встроенный шрифт,
  русские деления оси; PNG 200 dpi.
- `pdf.go` — `codeberg.org/go-pdf/fpdf` (туда переехал go-pdf; та же
  библиотека нужна gonum): A4 альбомный, высота строк и перенос таблиц с
  повтором шапки — руками, колонтитул с автором, датой и номером страницы.
- `pptx.go` — писатель OOXML поверх `template/blank.pptx`: пустой макет ищется
  по имени («Blank»/«Пустой») или по наименьшему числу placeholder'ов, размер
  слайда — из шаблона, короткая таблица делит слайд с KPI/графиком, длинная
  режется по 20 строк на слайд с нумерацией «(1/2)».
- `assets.go` — `go:embed` шрифтов DejaVu (лицензия в `fonts/LICENSE`) и
  шаблона.
- `render_test.go` — снимок из 25 сетей с длинными названиями, отрицательными
  копейками и «нет данных» за прошлый год; проверяет порядок блоков, лимиты,
  формат чисел, оба формата (PDF — сигнатура и число страниц, PPTX — zip,
  корректность всех XML, число слайдов и картинок, согласованность
  `sldIdLst` и `[Content_Types]`). `REPORT_SAMPLE_DIR=… go test ./reports`
  сохраняет файлы для глазной проверки.

Визуально проверен PDF (обе единицы); PPTX открыт в PowerPoint пользователем
на образцах спайка, итоговые файлы — на проверке.

## Критерии приёмки MVP

- КАМ не может сформировать или скачать отчёт по чужим сетям.
- Параметры фильтра в файле совпадают с запросом и доступной областью пользователя.
- KPI и графики совпадают с витриной для того же набора фильтров.
- Рядом с фактом и EAC показаны покрытие фактом и число месяцев без прогноза;
  «нет данных за прошлый год» (`nil`) не отображается как ноль.
- GTN, OPEX реестра и инвестиции промо остаются отдельными показателями.
- Отрицательные корректировки OPEX и значения с копейками не теряют знак и точность.
- При 20 строках таблицы текст не перекрывается и не выходит за границы страницы/слайда.
- Кириллица, длинные названия сетей и брендов отображаются корректно.
- PPTX открывается в Microsoft PowerPoint; PDF открывается стандартным просмотрщиком.
- После TTL файл недоступен, а запись задания и временный файл очищены.
- Ошибка renderer не оставляет пользователю частичный файл и показывает понятный статус.

## Риски и решения

| Риск | Решение |
| --- | --- |
| В PDF/PPTX цифры расходятся с экраном | строить оба формата из серверного `ReportSnapshot` |
| Слайд переполнен | фиксированные макеты, лимиты строк, перенос в приложение |
| PPTX по-разному выглядит на компьютерах | корпоративный шаблон, встроенные/разрешённые шрифты, визуальная QA |
| Сложный renderer не работает в контейнере | обязательный технический спайк до интеграции; шрифты встроены в артефакт |
| Для PPTX нет Go-библиотеки | спайк сравнивает ручную сборку OOXML и Python-воркер; решение до этапа 2 |
| Файлы доступны постороннему | проверка владельца на статусе и скачивании, случайные пути, TTL |
| Рендер съедает CPU процесса | лимит активных заданий на пользователя и на процесс |
| Рост набора блоков | реестр блоков и единый снимок данных, без копирования формул |
