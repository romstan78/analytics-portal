# План: рендер отчёта через HTML/CSS и headless Chromium (вариант C)

## Зачем

Портал собран на MUI-теме (`frontend/src/theme.ts`: Inter, `#6366f1`,
скруглённые карточки, тени, Recharts), и отчёт должен выглядеть как его печатная
версия — та же типографика, те же плитки и графики, та же плотность. Текущий
рендер (`backend/reports`, вариант A+B) собран из примитивов — прямоугольники,
линии, текст — и упирается в потолок: нет теней и скруглений с градиентами,
нет автоматической типографики (переносы, кернинг, межстрочные), каждый
элемент макета рисуется руками, а любое изменение дизайна витрины в отчёт не
попадает автоматически.

Вариант C убирает этот потолок: отчёт — это HTML-страница в стиле портала,
Chromium печатает её в PDF, а слайды PPTX собираются из её же снимков. Дизайн
делается CSS-ом, графики — тем же Recharts, что на витрине.

Это **план**, а не разрешение на изменение Docker-контура, зависимостей и
`package.json`: каждый такой шаг ниже помечен и требует отдельного «да».

## Что остаётся от текущей реализации

Не меняется ничего из «данных и заданий» — менялся только способ рисования:

- конструктор (`ReportExportDialog.tsx`), API `/api/reports*`, каталог блоков,
  `NormalizeReportRequest`, снимок `ReportSnapshot` и его хранение в
  `tbl_ReportJobs.snapshot_json`, фоновые задания, TTL, лимиты — как есть;
- страничная модель `reports/pages.go` (карточки, спецификации графиков, таблицы
  с оценками) остаётся источником правды для **PPTX-структуры** и запасного
  рендера; HTML-версия использует те же данные снимка.

Заменяется рендер: вместо `reports/pdf.go` + `reports/canvas.go` PDF печатает
Chromium с печатной страницы; `reports/pptx.go` получает картинки страниц.
Векторный рендер A+B остаётся запасным (`REPORT_RENDERER=vector`), пока C не
принят, и удаляется после приёмки — две реализации надолго не держим.

## Две ветви варианта C

| | C1 — HTML из Go-шаблонов | C2 — печатный маршрут фронтенда |
| --- | --- | --- |
| Кто рисует | `html/template` + свой CSS + SVG-графики, собранные в Go | React-страница `/print/report/:id` на тех же компонентах, что витрина: `KpiCard`, `ChartPaper`, `Sparkline`, Recharts |
| Соответствие порталу | приближённое: CSS переписывается вручную по мотивам темы MUI | точное: та же тема `modernTheme`, те же плитки и графики; изменения витрины попадают в отчёт сами |
| Зависимости | только Chromium | Chromium + доступ Chromium к фронтенду (или сборка печатной страницы в бандл) |
| Риск | дублирование дизайна в двух местах — расходится | страница должна рендериться без интерактива и дожидаться данных |

**Рекомендация — C2.** Требование «выгрузка должна соответствовать проекту»
буквально означает «те же компоненты». C1 даёт «похоже», C2 — «то же самое».

## Архитектура (C2)

```text
POST /api/reports ──► снимок (как сейчас) ──► ReportJob(queued)
                                                    │
                     runReportJob ──► chromedp ──► Chromium (отдельный контейнер)
                                                    │  открывает
                     http://frontend/print/report/:id?token=…
                                                    │  страница берёт
                     GET /api/reports/:id/snapshot   (снимок по одноразовому токену)
                                                    │  рисует React + Recharts,
                                                    │  ставит window.__reportReady
                     PDF: Page.printToPDF (A4 landscape, фон, поля 0, @page в CSS)
                     PPTX: по секции на слайд ─► screenshot секции 2× PNG ─► pptx.go
```

### Backend

- `reports/chrome/` — клиент Chromium через `chromedp` по remote DevTools
  (`CHROME_WS_URL`, например `ws://chromium:9222`); в бинарнике Chromium нет,
  образ backend не растёт.
- Токен печати: при создании задания генерируется одноразовый `print_token`
  (случайные 32 байта, хранится хэш в `tbl_ReportJobs` — новая миграция `036`),
  живёт до завершения задания. `GET /api/reports/:id/snapshot?token=` отдаёт
  `snapshot_json` только по нему и только пока задание `running`. Без JWT: у
  Chromium нет сессии пользователя, и давать её ему нельзя.
- `Page.printToPDF`: `landscape`, `printBackground`, `preferCSSPageSize`,
  без header/footer Chromium — колонтитулы рисует сама страница CSS-ом.
- PPTX: страница отдаёт список секций (`[data-slide]`), рендер снимает каждую
  через `Page.captureScreenshot` с `deviceScaleFactor: 2` в размер слайда и
  вставляет как картинку слайда; заголовок слайда и примечания — нативным
  текстом поверх (редактируемы), таблицы — нативные из страничной модели, как
  сейчас. Так PPTX выглядит как PDF, а текст и таблицы правятся.
- Тайм-ауты: страница 60 с, задание целиком 3 мин; при сбое Chromium —
  `failed` с понятным текстом, при `REPORT_RENDERER=vector` — запасной рендер.
- Конкурентность: один рендер за раз на процесс (Chromium держит вкладку и
  память); лимит заданий на пользователя как сейчас.

### Frontend

- Маршрут `/print/report/:id` вне `ProtectedRoute`: без шапки, меню, кнопок;
  данные — `GET /api/reports/:id/snapshot?token=` из query. В браузере
  пользователя этот маршрут тоже открывается (удобно для отладки и
  «предпросмотра перед печатью»), но только с токеном.
- `components/report/` — печатные компоненты: `ReportCover`, `ReportKpis`
  (на `KpiCard` + `Sparkline`), `ReportTrend` и `ReportBullets` (Recharts),
  `ReportTable`, `ReportMethodology`. Каждый блок — `<section data-slide>` с
  `break-after: page`.
- `print.css`: `@page { size: A4 landscape; margin: 12mm }`, отключение
  анимаций и hover, фиксированные размеры графиков (Recharts
  `ResponsiveContainer` заменяется явной шириной — он не умеет в print без
  layout-цикла), `-webkit-print-color-adjust: exact`.
- Готовность: страница выставляет `window.__reportReady = true` после того,
  как данные загружены, шрифт Inter (`document.fonts.ready`) применён и все
  графики отрисованы; рендер ждёт этого флага, а не таймера.
- Шрифт Inter сейчас подключается с Google Fonts (`frontend/index.html`);
  Chromium в контейнере без интернета его не получит и упадёт на Helvetica.
  Для печати Inter кладётся self-hosted в `frontend/public/fonts` (файлы уже
  есть в `backend/reports/fonts`, лицензия OFL) и подключается `@font-face`
  в `print.css`; обычные страницы могут остаться на CDN.

### Инфраструктура (требует разрешения)

- `docker-compose*.yml`: сервис `chromium` — `chromedp/headless-shell`
  (≈ 300 МБ, без GPU, `--remote-debugging-port=9222`), в сети с backend и
  frontend, наружу не публикуется. В демо-контуре — тот же сервис.
- `backend/go.mod`: `github.com/chromedp/chromedp`.
- `nginx.conf` фронтенда: SPA-fallback `try_files … /index.html` уже есть,
  `/print/*` попадает под него — правка не нужна.
- Переменные: `CHROME_WS_URL`, `REPORT_PRINT_BASE_URL`
  (`http://frontend/print/report`), `REPORT_RENDERER=chrome|vector`.

## Дизайн печатной страницы

Не изобретается — берётся с витрины:

- сетка плиток и заголовки как в `NetworkDashboardView` (те же `KpiCard`,
  подписи «Обязательство по контракту», «Факт отгрузок» и т. д.);
- графики: «Динамика по кварталам/месяцам» — тот же Recharts-компонент,
  что на витрине, в фиксированной ширине; топы — горизонтальные bullet-бары
  (Recharts `BarChart layout="vertical"` с двумя слоями и `ReferenceLine`
  для EAC);
- таблицы — тот же стиль, что у `NetworkQuarterTable`/DataGrid (без
  виртуализации: DataGrid в печати не годится, нужна простая `<table>` с теми
  же классами);
- шкала чисел, оценки цветом, копейки только в приложении — правила из
  `reports/theme.go` переносятся в `utils/reportFormat.ts` (это форматирование,
  не расчёт — инвариант «расчёты только на бэкенде» не нарушается: числа
  приходят из снимка готовыми);
- титул с тремя главными плитками; колонтитул с названием, автором, датой и
  номером страницы (`counter(page)`).

2. Проверить: шрифт Inter, Recharts в print, `@page`, фон, время рендера,

3. Зафиксировать образ, флаги, тайм-ауты.

#### Результаты спайка (17.09.2026, демо-контур, 57 сетей)

Спайк-код — вне репозитория (`scratchpad/spike`, Go + `chromedp v0.16.0`);
контейнер удалён после проверки.

- Образ `chromedp/headless-shell:latest` (Chrome 151, **146 МБ**, не 300).
  Entrypoint `run.sh` сам задаёт `--no-sandbox`, `--remote-debugging-port` и
  проксирует 9222 через socat; свои флаги передаются как `command` **дополнительно**,
  а не вместо (переопределение порта ломает socat). Нужны `--disable-dev-shm-usage`
  и `shm_size: 512m`.
- Витрина «Итоги» в headless: открытие 0,15 с, данные + Recharts дорисованы за
  **1,3–2,1 с**, `printToPDF` **80–135 мс** (415 КБ, 4 страницы A4 альбомных),
  снимок секции 2× (2434×852) **0,4 с, 80 КБ**. Всё вместе < 4 с — запас до
  критерия «30 с» большой.
- Память контейнера: 85 МБ в покое, пик 560 МБ на полноэкранном снимке 2×
  (5168 px высотой); посекционные снимки — без пика. Лимит 1 ГБ достаточен.
- В PDF сохраняются тени, скругления, градиенты спарклайнов, SVG Recharts
  (векторно), Inter встроен. Print-media перестраивает MUI-сетку под ширину
  листа, а `ResponsiveContainer` мерит ширину до печати и обрезает правый край —
  подтверждает пункт про фиксированные размеры графиков.
- `landscape: true` поворачивает **портретный** лист: `paperWidth/Height`
  задаются как 8.27×11.69, либо `preferCSSPageSize` с `@page { size: A4 landscape }`.
- Google Fonts отдаёт Inter переменным шрифтом: Chromium вшивает все веса как
  сабсеты `Inter-Regular` (31 штука). Со статическими self-hosted
  `Inter-Regular`/`Inter-SemiBold` это уйдёт. CDN из контейнера на этой машине
  доступен, на сервере — не гарантирован; self-hosted обязателен.
- CORS/адрес API: бандл собран под `localhost:8081`, из контейнера Chromium это
  недостижимо; в спайке запросы перепиcаны через Fetch domain (`interceptResponse`
  + подмена `Access-Control-Allow-Origin`). В проекте — вариант «а»: nginx
  фронтенда проксирует `/api/reports/*/snapshot` на `backend:8080`, страница
  печати ходит по относительному пути, CORS не участвует.
- Готовность страницы: `document.fonts.ready` + два `requestAnimationFrame` +
  наличие `.recharts-surface path` сработали стабильно — та же логика ляжет в
  `window.__reportReady`.

### Этап 2. Печатный маршрут во фронтенде

1. `/print/report/:id` + `components/report/*` + `print.css`.
2. Флаг готовности `__reportReady`, `document.fonts.ready`.
3. Storybook-подобный стенд не нужен: маршрут открывается в браузере с
   токеном — это и есть предпросмотр.

**Сделано 17.09.2026.** Отступление от текста плана: страница печати получает
не сырой снимок, а **печатную модель** `models.ReportPrint` — результат
`reports.BuildPages`, переведённый в JSON (`reports/print.go`). Иначе 640 строк
`pages.go` (подписи, колонки, шкалы, примечания) пришлось бы повторить на TS, и
две копии разошлись бы. Фронтенд рисует страницы обобщённо: `ReportCards`
(на `KpiCard`), `ReportChart` (Recharts: динамика, bullet, водопад — явные
размеры), `ReportTable`, `ReportSection`, `ReportDocument`; числа приходят
готовыми строками, осям отдаётся шкала. `utils/reportFormat.ts` — только
подписи осей и цвета тонов. Endpoint `GET /api/reports/:id/print?token=` —
этап 3. Проверено в браузере на фикстуре (`print_test.go` пишет
`sample-print.json` при `REPORT_SAMPLE_DIR`); печатный режим (`@page`,
разрывы, колонтитул, `@bottom-right` со счётчиком страниц) проверяется на
этапе 3 живым Chromium — из сессии стенд наружу не публикуется.

### Этап 3. Backend-рендер

1. Миграция `036`: `print_token_hash`, `print_token_expires_at`.
2. `GET /api/reports/:id/print` по токену (печатная модель, см. этап 2);
   nginx фронтенда проксирует этот путь на backend (вариант «а»).
3. `reports/chrome`: PDF через `printToPDF`, снимки секций для PPTX.
4. `pptx.go`: слайд = картинка секции + нативные заголовок, примечания,
   таблица; титул — нативный текст.
5. `REPORT_RENDERER` и запасной векторный рендер; тесты с фейковым Chromium
   (интерфейс `printer`).

### Этап 4. Приёмка

1. Визуальное сравнение «витрина ↔ PDF ↔ слайд» на демо: те же плитки, те же
   числа, те же цвета.
2. Открытие PPTX в PowerPoint, PDF в Acrobat/Preview; размер файла
   (растровые слайды 2× — ориентир ≤ 15 МБ на 20 слайдов).
3. Сценарии сбоя: Chromium недоступен → `failed` с текстом; токен истёк →
   `403`; страница не готова за 60 с → `failed`.
4. README: раздел о Chromium, переменных и предпросмотре; project.md.
5. Удалить векторный рендер после приёмки (`canvas.go`, `pdf.go`), оставив
   `pages.go` для структуры PPTX.

## Критерии приёмки

- Отчёт неотличим по стилю от витрины: шрифт, цвета темы, плитки, графики
  Recharts; на одной странице — не больше, чем на одном экране витрины.
- Числа совпадают с витриной (тот же снимок, что и сейчас).
- КАМ без закрепления — `403`; снимок отдаётся только по одноразовому токену и
  только пока задание готовится.
- PDF: A4 альбомный, страница на блок, длинные таблицы переносятся с повтором
  шапки (`thead` + `break-inside: avoid`).
- PPTX: слайд на секцию, заголовок и примечания редактируемы, таблицы
  нативные, картинка секции чёткая при 200 %.
- Рендер отчёта на 57 сетях — не дольше 30 с; сбой Chromium не роняет
  backend и не оставляет частичный файл.

## Риски

| Риск | Решение |
| --- | --- |
| Chromium не видит фронтенд/шрифты в контейнере | сервисы в одной сети, Inter self-hosted; спайк проверяет до интеграции |
| Recharts не дорисовал к моменту печати | явный флаг готовности после `requestAnimationFrame` × 2 и `fonts.ready`, а не таймер |
| Снимок утекает по ссылке печати | одноразовый токен с TTL, хэш в БД, выдача только в `running` |
| Растровые слайды тяжёлые | 2× PNG, JPEG для слайдов без текста, лимит слайдов; таблицы нативные |
| Память Chromium при больших отчётах | один рендер за раз, `--disable-dev-shm-usage`, лимит памяти контейнера |
| Две реализации рендера | векторная удаляется на этапе 4; до этого включается флагом |
