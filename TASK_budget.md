# Задача: раздел «Бюджет»

> Уточнение постановщика при реализации (14.09.2026): для каждой версии
> пользователь **сам выбирает по кварталам отдельно источники ТО и контрактного
> GTN: план, факт или прогноз реестра; для ТО также факт одного из каналов
> OLAP**. Дата не назначает источник автоматически. Например, факт OLAP SS
> Q1–Q2, прогноз реестра Q3–Q4. Для выбранного факта GTN берётся
> оплата реестра; обычная оплата не складывается с квартальным прогнозом.
> Годовой кумулятив — отдельная доплата Q4 по существующему правилу, с вычетом
> оплат Q1–Q3 и прогноза Q4, без отрицательного остатка. Промо: факт инвестиций,
> если он есть, иначе план; OPEX: бюджет. Это уточнение имеет приоритет над
> первоначальным описанием автоматического каскада ниже.

Документ самодостаточный — рассчитан на исполнение в отдельной сессии, без
контекста обсуждения, в котором он родился (13–14.09.2026). Решения
постановщика в нём зафиксированы; повторно их не обсуждать, спрашивать только
о том, чего здесь нет.

Макет, по которому строится экран: `TASK_budget_mockup.html` (рядом с этим
файлом, открывается в браузере) — тот же макет опубликован как артефакт
https://claude.ai/code/artifact/4917a6c2-78ab-4598-a78d-3773765d31ee. Цифры в
макете — демо-контур, прогнозы и оплаты условные; смотреть на структуру,
подписи и поведение, а не на суммы.

## Что должно получиться

Новый раздел портала **«Бюджет»** — плитка на главной рядом с «Реестр сетей»,
маршрут `/budget`. Один экран:

1. **Таблица «бренд × квартал».** Слева бренды (`brand_as`), у каждого полоса
   из трёх строк — **ТО / Инвестиции / %**; сверху Q1–Q4 и «Год». Внизу «Итого».
   Бренд раскрывается в сети (сеть → ссылка на карточку реестра).
2. **Версии бюджета** за год: `B` (бюджет, до начала года), `F1`, `F2`, `F3`
   (прогнозы после закрытия квартала) и «Текущее» — незамороженный черновик,
   который читает реестр живьём. Псевдоверсия «Факт прошлого года» — для
   сравнения с `B`.
3. **Сравнение двух версий** в той же таблице: колонка квартала делится на
   `A | B | Δ` (Δ — абсолют или %; у строки `%` — п.п.).
4. **Правка кликом** по ячейке ТО или инвестиций бренда в открытом квартале
   черновой версии; правка живёт в версии, в реестр не пишется.
5. **Панель промо** справа: какие промо стоят за суммой промо-инвестиций
   бренда/портфеля за квартал, топ по весу, чекбокс «в бюджете», в режиме
   сравнения — F2 | B | Δ и метки «новое / снято / изменено / факт вместо
   плана / исключено».
6. **Excel** — файл равен экрану, четыре листа.

Фильтры над таблицей: год · версия · сравнить с · тип сети · база процента ·
инвестиции (источник × тип) · состав (свёрнут/развёрнут) · НДС.

## Решения постановщика (не пересматривать)

| # | Решение |
| --- | --- |
| 1 | Видимость: **не для КАМ**. Роли `admin`, `agreement1`, `agreement2` и новая роль `analyst`. Область по КАМу не применяется — портфель целиком. Правят и замораживают версии `admin` и `analyst`; `agreement1/2` читают. |
| 2 | НДС по умолчанию — **без НДС**; «с НДС» переключателем. |
| 3 | **Факт OPEX = план** (у OPEX-бюджета факта нет по определению). |
| 4 | **Факт GTN** — где по реестру уже оплачено (`paid_investments_rub`), остальное — прогноз по правилу ступеней (`forecast_investments_rub`). Частичная оплата — факт оплаченного + прогноз остатка. Годовая доплата по кумулятиву входит в Q4. |
| 5 | Из промо берём **только инвестиции**: факт, если есть, иначе план; делим на GTN/OPEX по `gtn_opex`. Аплифт, план/факт промо-продаж — не берём. |
| 6 | Инвестиции = контракт GTN + контракт OPEX + промо GTN + промо OPEX. На экране переключатели «источник (всего/контракт/промо) × тип (всего/GTN/OPEX)»; «развернуть состав» показывает четыре строки. |
| 7 | Источник ТО выбирается в составе версии отдельно по каждому кварталу: план / факт / прогноз реестра либо факт конкретного канала OLAP (SS / SS wo Ecom / PURE / OMNI / MP). Он определяет и строку ТО, и знаменатель процента на обеих вкладках. Отдельный фильтр «Оценка ТО реестра» (цена контракта / цена OLAP) применяется только к кварталам с источником из реестра; у будущих кварталов процента нет. |
| 8 | Правка ТО пересчитывает контрактный GTN по эффективной ставке бренда (GTN/ТО базового значения); OPEX и промо не меняются. Правка суммы инвестиций (свёрнутый состав) меняет контрактный GTN; при развёрнутом составе правится компонент. Промо-строки числом не правятся — только выбором промо. |
| 9 | Правится только черновик, только открытые кварталы, только у бренда; год — сумма. Правка доступна при всех типах сетей, в цене контракта и без НДС; в базу ложится «сеть × бренд × квартал» пропорционально. |
| 10 | Версия = замороженный снимок реестра + правки, хранится на уровне «сеть × бренд × квартал» и **промо построчно**. Черновик читает реестр живьём; заморозка фиксирует всё, включая цены OLAP месяца заморозки. |
| 11 | Статусы промо сводятся к четырём: проведено → согласовано → на согласовании → черновик; отклонённые/отменённые не входят. Умолчание: первые три в бюджете, черновики нет; аналитик меняет по одному или массово. Таблица соответствий — справочник, не код. |
| 12 | Excel: бэкенд, `excelize`, из того же ответа, что у экрана. Листы «Бюджет», «Данные» (плоско, уровень сети), «Промо» (построчно), «Параметры». Δ и % — значения, не формулы. Импорт из Excel — не в этом этапе. |
| 13 | Таблица одна, графиков нет. |

Открыто (спросить у постановщика, когда дойдёт дело): правило против двойного
счёта, если промо-скидка выплачивается через тот же контрактный бонус за объём.

## Данные: откуда берётся каждая величина

Все суммы — млн ₽ на экране, в базе — рубли. Инвестиции складываются по сетям
только в базе «без НДС» (у сетей разные ставки); «с НДС» — вторая колонка тех же
таблиц.

| Величина | Источник | Правило |
| --- | --- | --- |
| ТО план | `tbl_NetworkPlans.plan_rub` / `plan_units` | Итог портфеля — обязательство по контракту: валовый пул целиком (строка `brand_as IS NULL`) + отдельные бренды. Сумма брендов отличается на нераспределённый остаток пула — в таблице отдельная строка «Нераспределённый остаток пула», чтобы «Итого» сходилось с реестром. Уже считает `NetworkPlanTotals.ContractPlanRub` / `Undistributed`. |
| ТО факт | `tbl_NetworkMonthlyFacts` (руб + уп), свод в `tbl_NetworkPlans.fact_rub` | Закрытые месяцы. Витрина реестра берёт факт из помесячной таблицы, не из квартальной колонки — делать так же. |
| ТО ожидание (EAC) | факт закрытых месяцев + прогноз открытых | Прогноз месяца: официальный (`tbl_NetworkForecasts`, строка без SKU) → системный (`recommendedForecastMetric`: среднее прошлого года и скользящего среднего + промо-аплифт) → факт. Это `valueForEAC` в `services/network_forecast_service.go`; витрина реестра на уровне бренда уже так считает (`buildNetworkSlice`). |
| ТО в цене OLAP | `plan_units` / `fact_units` / `forecast_units` × цена OLAP SS SKU | Цена — `SUM(руб)/SUM(уп)` по SKU из `tbl_EcomSalesNormalized`, сегмент `OLAP SS`, за месяц (`getGlobalOlapSSSKUPrices` в `repository/network_monthly_repo.go`). Бренд с вводом по SKU — точно; бренд с вводом на уровне бренда — через `brandWeightedPrice` (уже есть в прогнозе). В демо цены контракта = OLAP SS, разницы не видно. |
| GTN контракт: план | `plan_investments_rub[_net]` | план × процент, порога нет. |
| GTN контракт: факт/прогноз | `paid_investments_rub` → `forecast_investments_rub[_net]` | Каскад по ячейке «сеть × бренд × квартал»: есть оплата — факт (маркер ✓), нет — прогноз по правилу ступеней (○), частично — сумма (◐). У `paid_investments_rub` нет колонки «без НДС» — приводить ставкой квартала сети (`NetRub`). Годовая доплата: `CalculateNetworkAnnualInvestmentCumulativeForNetwork` → `TotalSupplementRub` — прибавить к прогнозу Q4 сетей с `has_annual_investment_cumulative`. |
| OPEX контракт | `tbl_NetworkOpexBudgets` (`amount_rub`, `amount_rub_net`, помесячно) | Квартал — сумма месяцев. Факт = план. |
| Промо GTN / OPEX | `tbl_PromoActivities` | `CASE WHEN actual_investments > 0 THEN actual_investments ELSE plan_investments_rub END`; тип — префикс `OPEX` в `gtn_opex`, всё остальное GTN; НДС — ставкой квартала сети. Это уже делает `dashboardPromos` + `promoNetRub` в витрине реестра. Связь с реестром — по `network_name` = `tbl_Networks.name`. |
| Тип сети | `tbl_NetworkGeoMapping.network_type` | Значения: `Chain Pharm` (40), `Аптечная сеть` (8), `E-Retailer` (6), `Group Pharm` (5), `Marketplace` (1). Связь по имени сети, ID нет. **Не путать** с `tbl_Networks.network_type` (`regular`/`warehouse` — тип контракта). |
| Интернет-продажи | `tbl_EcomSalesNormalized` | `un_rub = 'руб'`; сегменты `OLAP SS`, `OLAP SS wo Ecom`; каналы `PURE`, `MP`, `OMNI`. Бренд — через `productName → tbl_SKUMapping.sku → brand_as` (в продажах `brandName` = `tbl_SKUMapping.brand`, не `brand_as`). Только закрытые месяцы; будущее — пусто. |
| Прошлый год | те же таблицы, `year − 1` | ТО факт, GTN оплаченный, OPEX, промо факт. |
| Закрыт / текущий / будущий | `isClosedForecastMonth` (`services/network_forecast_service.go`) | Закрыт месяц строго раньше текущего; квартал закрыт, если закрыты все три; текущий — часть месяцев закрыта. |

Цифры демо-контура для сверки (гросс, как в базе): план по контракту 2026 —
Q1 8 523,8 / Q2 7 460,0 / Q3 7 453,0 / Q4 8 824,4 млн (пул 1 876,4 + отдельные
6 647,4 в Q1); факт 2026 — Q1 8 369,1 / Q2 7 481,9 / Q3 2 372,3 (загружен по
июль); GTN план Q1 795,6, по правилу 382,3, оплачено 882,4; OPEX 221,82 млн в
каждом квартале 2026; промо Q3 2026 бренда «Демо-бренд 08 «Орион»» — 250 промо,
GTN 164,93 + OPEX 2,11; портфель Q3 — 912 промо, 267,4 млн; OLAP SS 2026 —
39 298,8 млн.

Ответ `GET /api/budget` (эскиз `models/budget.go`, имена уточнить по коду):

```go
type BudgetResponse struct {
    Year, Version, Compare, Params…                       // что запросили, как в SalesPivotResponse
    QuarterStates [4]string                               // closed | current | future | budget (для версии A и B отдельно)
    Brands []BudgetBrand                                  // полоса бренда
    PoolRemainder BudgetLine                              // нераспределённый остаток пула (только ТО план)
    Total BudgetBrand
    ForecastCoveragePct *float64                          // доля ячеек Q с официальным прогнозом
}
type BudgetBrand struct {
    Brand string
    To, Sales BudgetLine                                  // Sales заполняется при базе «продажи»
    GtnContract, OpexContract, GtnPromo, OpexPromo BudgetLine
    Investments BudgetLine                                // по выбранным источнику × типу
    Pct BudgetLine                                        // инвестиции / база, %
    Networks []BudgetBrand                                // раскрытие, только по запросу
}
type BudgetLine struct {
    Q [4]BudgetCell; Year BudgetCell
}
type BudgetCell struct {
    A, B *float64; Delta *float64                         // B и Delta — в режиме сравнения
    Mark string                                           // paid | partial | forecast | budget | none
    Edited *BudgetEdit                                    // {Base, Value, Who, When}
    Editable bool
}
```

- `tbl_BudgetVersions(id, year, code B|F1|F2|F3|LIVE, name, status draft|frozen, frozen_at, created_by, created_at, updated_at)`; уникально `(year, code)`.
- `tbl_BudgetLines(version_id, network_id, brand_as, quarter, metric, value_rub, value_net, value_units, mark, source registry|manual, updated_by, updated_at)` — снимок и правки в одной таблице, `source` различает; `metric` ∈ {to, gtn_contract, opex_contract, gtn_promo, opex_promo, sales_ss, sales_sswo, sales_pure, sales_omni, sales_mp}. Пул — строка с `brand_as NULL`.
- `tbl_BudgetPromoLines(version_id, promo_id, network_id, brand_as, quarter, month, gtn_opex, status_norm, plan_rub, fact_rub, budget_rub, budget_net, included, included_by, updated_at)`.
- `tbl_BudgetOlapPrices(version_id, sku, price, source_year, source_month)` — цены OLAP на момент заморозки.
- `tbl_BudgetPromoStatusMap(raw_status, agreement_rule, status_norm)` — справочник нормализации; заполняется по факту данных (`SELECT DISTINCT status, agreement1_status, agreement2_status FROM tbl_PromoActivities`).

Черновик (`draft`) хранит **только** строки `source = manual` и промо с изменённым
`included`; всё остальное читается из реестра при каждом запросе. Заморозка
дописывает строки `source = registry` для всех ячеек и промо, после чего версия
только читается. Так черновик никогда не расходится с реестром, а замороженная
версия не меняется от прайса и загрузок.

возвращает пересчитанную полосу бренда и «Итого»).

## Правила расчёта (точные)

Обозначения на ячейку «бренд × квартал» (агрегат по сетям среза):

- `TO_plan = Σ plan_rub` (для «Итого» — обязательство по контракту).
- `TO_eac = Σ по месяцам: closed ? fact : (official ?? system ?? fact)`.
- `GTN_contract = Σ по сетям: paid > 0 ? paid_net + (partial ? forecast_rest : 0) : forecast_investments_net`; для Q4 + доплата кумулятива. Маркер ячейки: `paid` если все строки оплачены, `partial` если часть, `forecast` иначе; в замороженной версии — то, что было на момент заморозки.
- `OPEX_contract = Σ amount_net месяцев квартала`.
- `Promo_GTN/OPEX = Σ по промо: included ? net(fact > 0 ? fact : plan) : 0`.
- `Investments = выбранные компоненты`; `% = Investments / Base × 100`, где `Base` — `TO_eac` (или `TO_plan` в версии `B`, или продажи канала); `Base = 0/null → % = null`.
- Год: суммы; `%` года — из сумм, не среднее процентов.
- Δ: `A − B` или `(A/B − 1) × 100`; для `%` — `A − B` в п.п.
- Правка ТО бренда: `rate = GTN_contract_base / TO_base`; `GTN_contract_new = rate × TO_new`; раскладка по сетям — пропорционально базовым значениям сети.
- Правка инвестиций (свёрнуто): `GTN_contract_new = value − OPEX − Promo_GTN − Promo_OPEX`.
- ТО в цене OLAP: `Σ SKU units × olap_price(month)`; бренд без SKU-ввода — `units × brandWeightedPrice`. Инвестиции от базы цены не зависят.
- «С НДС»: инвестиции контракта — `*_rub` вместо `*_net`; промо — как введено; ТО не меняется.

## Подводные камни (проверено на этом проекте)

- **Комментарий в `models/network_dashboard.go` про EAC устарел**: там сказано,
  что месяц без прогноза добавляет только факт, но `buildNetworkSlice` на уровне
  бренда уже берёт системный прогноз (`valueForEAC(closed, fact, official,
  system)`); без системного — только SKU-детализация. Бюджет опирается на
  брендовый уровень, поэтому правило ожидания совпадает с витриной.
- Официальных прогнозов в демо почти нет (2 сети из 60) — ожидание Q3–Q4 на
  демо почти целиком системное. Показывать `ForecastCoveragePct`.
- `paid_investments_rub` в демо сгенерирован без порога и превышает план;
  на проде придёт иначе. Тесты писать на фикстурах, не на демо-числах.
- Пул: у 6 сетей валовый пул, бренды разбирают его не точно. Без строки остатка
  «Итого» не сойдётся с реестром, и первое, что сделает постановщик, — сверит.
- Тип сети живёт в другой таблице и связан по имени; сеть без строки в
  `tbl_NetworkGeoMapping` попадает в тип «(не задан)» — не терять её из «Итого».
- Бренд продаж — через `tbl_SKUMapping.brand_as`, SKU без сопоставления —
  в «Без бренда» (так делает `getGlobalOlapSSSKUPrices`).
- Статус промо — свободный текст с разным регистром («финализировано» и
  «Финализировано»); нормализовать через `LOWER(LTRIM(RTRIM()))`. Фильтр
  `status <> 'cancelled'` в `dashboardPromos` реальному словарю не соответствует
  — в справочнике нормализации предусмотреть «отменено/отклонено».
- Промо и реестр связаны по `network_name`; промо на сети, которой нет в
  реестре, в бюджет не попадает — как в витрине.
- Пул соединений один на приложение: срез года — один вызов
  `GetNetworkDashboardData`, не веер запросов по брендам.
- `frontend/src/types/api.generated.ts` руками не править; после моделей —
  `make types`, иначе `make test` упадёт на `types-check`.
- Продажи в демо есть на все 12 месяцев 2026 (сгенерированы), на проде — только
  закрытые; правило «будущее — пусто» проверять датой, а не наличием данных.

## Критерии готовности этапа целиком

1. Аналитик открывает «Бюджет», КАМ раздела не видит и получает `403`.
2. Таблица «живой» версии сходится с витриной реестра и с промо-реестром (числа
   выше в разделе «Данные»); переключатели меняют состав и базу процента.
3. Версия замораживается и после этого не меняется; черновик меняется.
4. Сравнение показывает `A | B | Δ` с правильной окраской; `B` сравнивается с
   фактом прошлого года.
5. Правка ТО/инвестиций и выбор промо меняют полосу бренда и «Итого»;
   ограничения возвращают понятную причину; гонка — `409`.
6. Панель промо: топ по весу с концентрацией, статусы, массовые действия,
   режим сравнения с метками, ссылки в промо-реестр.
7. Excel равен экрану; `make test` зелёный; тесты сервисов на фикстурах покрывают
   правила из раздела «Правила расчёта».
