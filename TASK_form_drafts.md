# Задача: не терять введённое в формах

Документ самодостаточный — рассчитан на исполнение в отдельной сессии, без
контекста предыдущего разговора.

## Проект

Аналитический портал: Go 1.25 + Gin + MSSQL (`backend/`), React 19 + TypeScript 6
+ Vite 8 + MUI 9 (`frontend/`). Демо-контур — `docker-compose.demo.yml`
(backend :8081, frontend :5174), команды в `Makefile` (`make demo-up`,
`make demo-bootstrap-user`). Проверки: `make test` — Go-тесты, eslint, vitest,
сборка фронтенда, python-тесты.

## Задача 1 (основная). Черновик формы переживает обрыв

### Проблема

Заполненная карточка промо живёт только в памяти вкладки. Данные пропадают,
если:

- истёк refresh-токен — `fetchWithAuth` в `frontend/src/api/promo.ts` делает
  `logout()` и `window.location.replace('/login')` прямо посреди работы;
- пользователь случайно закрыл вкладку или обновил страницу;
- оборвалась сеть, браузер выгрузил вкладку.

Возврат **на прерванный раздел** уже сделан (`frontend/src/utils/returnPath.ts`),
но форма при этом открывается пустой. Сценарий обидный: КАМ заполняет два
десятка полей карточки, отвлекается, возвращается — и начинает заново.

Та же проблема у сетки «План и факт» в реестре сетей
(`frontend/src/pages/NetworkRegistry.tsx`), где значения вносят массово и
сохраняют одной кнопкой.

### Что уже есть в коде (использовать, не изобретать)

| Что | Где | Зачем пригодится |
| --- | --- | --- |
| `userScopedKey(base)` | `frontend/src/utils/storage.ts` | ключи хранилища, привязанные к пользователю: без этого черновик одного человека открылся бы у следующего вошедшего в ту же вкладку |
| `returnPath.ts` | `frontend/src/utils/` | образец работы с хранилищем: `try/catch` вокруг каждого обращения, чистые функции отдельно от побочных эффектов, тесты без DOM |
| `usePromoForm` | `frontend/src/hooks/` | состояние формы карточки промо |
| `PromoEditDialog` | `frontend/src/components/` | сама форма; ввод обрабатывает `handleFieldChange` |
| `usePromoCalculations` | `frontend/src/hooks/` | расчётные поля приходят **с сервера** (`POST /api/promo/calculate`), в форму их кладёт ответ |

### Что сделать

1. **Сохранять черновик** формы карточки промо в `localStorage` при изменении
   (debounce ~500 мс). Ключ — через `userScopedKey`, с идентификатором записи:
   у новой карточки и у промо №994 черновики не должны пересекаться.
2. **Предлагать восстановление** при открытии формы, если черновик есть и
   отличается от того, что пришло с сервера. Именно предлагать, а не
   подставлять молча: пользователь должен понимать, откуда взялись значения.
   Показывать время сохранения.
3. **Удалять черновик** после успешного сохранения и по явному отказу от
   восстановления.
4. **Предупреждать при закрытии вкладки** (`beforeunload`), если есть
   несохранённые изменения.
5. **Срок жизни** — 7 дней; при чтении просроченный черновик молча
   выбрасывается.

### Подводные камни (проверено на этом проекте)

- **Не сохранять расчётные поля** (`plan_roi`, `plan_promo_uplift_rub`,
  `actual_roi`, …). Их считает сервер, и восстановленные из черновика они могут
  разойтись с формулой. Хранить только то, что пользователь вводит руками.
- **`localStorage` бывает недоступен** (приватный режим, запрет на хранилище) —
  каждое обращение в `try/catch`, как в `returnPath.ts`. Отсутствие хранилища
  не должно ломать форму.
- **eslint запрещает синхронный `setState` в эффекте** (правило
  `react-hooks/set-state-in-effect`). Восстановление черновика делайте в
  обработчике открытия формы или через ref, а не в `useEffect` с прямым
  `setForm`.
- **eslint не ловит неимпортированные хуки** — после правок обязательно
  `npm run build`, одного `npm run lint` мало.
- **Ключ обязан включать пользователя.** В той же вкладке может войти другой
  человек; чужой черновик показывать нельзя.
- Не трогать поля согласования (`agreement1`, `agreement2`) и историю
  комментариев — они приходят с сервера и правятся отдельным процессом.

### Критерии готовности

- [ ] Заполнил половину карточки → обновил страницу → форма предлагает
      восстановить и восстанавливает введённое.
- [ ] Сохранил карточку → черновик исчез, повторное открытие чистое.
- [ ] Вошёл другим пользователем в той же вкладке → чужой черновик не
      предлагается.
- [ ] Форма работает при недоступном `localStorage` (проверить приватным окном
      или заглушкой, бросающей исключение).
- [ ] Расчётные поля после восстановления пересчитаны сервером, а не взяты из
      черновика.
- [ ] Тесты на чистые функции (сериализация, срок жизни, разбор чужого
      пользователя) — по образцу `frontend/src/utils/returnPath.test.ts`.
- [ ] `make test` зелёный.
- [ ] Проверено на демо-контуре, а не только тестами.

### Как проверить на демо

```bash
make demo-up
make demo-bootstrap-user   # логин и пароль задаются в .env: DEMO_BOOTSTRAP_*
```

Интерфейс — <http://localhost:5174>. Карточка открывается по клику на строку
таблицы: «Анализ промо» → «Просмотр данных».

Сценарий обрыва сессии воспроизводится так: войти, открыть форму, заполнить,
затем в консоли браузера `localStorage.setItem('token','broken.token')` и в БД
пометить refresh-сессии отозванными:

```sql
UPDATE dbo.tbl_RefreshSessions SET revoked_at = GETUTCDATETIME(), revoke_cause = 'user_revoked'
WHERE username = '<логин>' AND revoked_at IS NULL;
```

Следующий запрос уведёт на форму входа — после повторного входа черновик должен
предлагаться к восстановлению.

## Задача 2. Ключ идемпотентности на сохранение промо

Пользователь нажимает «Сохранить», ответ не доходит из-за сети, он жмёт снова —
и создаётся дубль. Сейчас дубли вычищает офлайн-скрипт
`sync_script/dedupe_promo.py`, то есть постфактум.

**Что сделать:** клиент генерирует UUID на открытие формы и шлёт его в
`POST /api/promo/save`; сервер сохраняет ключ рядом с записью и на повтор с тем
же ключом возвращает прежний результат вместо второй вставки. Ключ нужен только
для вставки — при обновлении от дублей защищает `updated_at` (optimistic
locking, уже есть).

Хранение ключа — отдельная таблица или колонка в `tbl_PromoActivities` с
уникальным индексом; миграции лежат в `backend/migrations/`, формат goose.
**Важно:** блоки `BEGIN…END` в миграции обязательно оборачивать в
`-- +goose StatementBegin` / `-- +goose StatementEnd`, иначе goose режет SQL по
`;` и миграция падает.

## Задача 3. Состояние фоновых выгрузок — в БД

Сейчас реестр заданий живёт в памяти процесса
(`backend/handlers/sales_export_jobs.go`): после перезапуска опрос статуса даёт
404, выгрузку надо запускать заново. Это описано в README как известное
ограничение.

Пока приложение работает в один процесс — это неудобство. При появлении второй
реплики задание начнёт теряться штатно: клиент опросит статус у соседа, который
о задании не знает. Переносить состояние в БД лучше **до** масштабирования.

Образец рядом: `backend/repository/login_attempts_repo.go` — таблица, чистые
функции правил отдельно от SQL, тесты на них без базы.

## Общие правила по проекту

- Ветку от `main`, коммиты на русском, в сообщении — причина, а не только факт.
- `make test` перед коммитом; проверка на демо-контуре обязательна.
- Комментарии в коде объясняют «почему», а не «что»: это стиль всего
  репозитория.
- Контракт API описан в Go-структурах, TypeScript-типы генерируются
  (`make types`), расхождение ловит `make types-check` в CI.
