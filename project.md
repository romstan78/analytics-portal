# Analytics Portal

## Стек
- **Backend:** Go 1.25 + Gin + MSSQL (go-mssqldb) + squirrel + excelize + golang-jwt + goose
- **Frontend:** React 19 + TypeScript 6 + Vite 8 + MUI 9 + Recharts 3 + React Query 5
- **Infra:** MSSQL (dbo.tbl_PromoActivities), Docker (docker-compose.yml), локальный сервер localhost:8080/5173;
  отдельный демо-контур — docker-compose.demo.yml, localhost:8081/5174

> Версии сверяются с `backend/go.mod` и `frontend/package.json`. Если правите
> стек — правьте и здесь: расхождение этого файла с фактом уже было предметом
> аудита.

## Архитектура
```
frontend/           backend/
├─ src/
│  ├─ api/          ├─ main.go            (роутинг, rate limiter)
│  ├─ components/   ├─ config/            (DB, cache, auth, logger)
│  ├─ hooks/        ├─ handlers/          (Gin, HTTP-хендлеры)
│  ├─ pages/        ├─ middleware/        (JWT + RoleRequired)
│  ├─ types/        ├─ models/            (типы + хелперы PtrFloat/PtrInt)
│  └─ utils/        ├─ repository/        (SQL-запросы)
│                   ├─ services/          (DTO, расчёты, MergeDTO)
│                   └─ migrations/        (SQL-файлы + ensureTables())
└─ sync_script/     (импорт данных из внешних источников)
```

**Ключевые точки:**
- `tbl_PromoActivities` — основная таблица промо-акций
- `tbl_PromoComments` — новая таблица комментариев (запись в неё + дублирование в comments)
- `tbl_AuditLog` — аудит изменений
- Комментарии: старый формат `[DD.MM.YYYY роль|автор]: текст` в поле comments, новый — в tbl_PromoComments
- `applyJSONToRow` — switch для UPDATE (пропускает comments, согласования)
- `services/MapToDTO` → `DTOToDBRow` — для INSERT
- `MergeCalculatedIntoDBRow` — запись вычисляемых полей
- `DBRowToDTO` → `CalculateFields` — пересчёт при UPDATE
- Optimistic Locking через `updated_at`

## Выполненные изменения (16.08.2026)

### Этап 4: целостность согласований

- Одиночное и массовое согласование требуют актуальный `updated_at`; устаревшая карточка получает `409 Conflict`.
- Массовое согласование выполняется одной транзакцией: при конфликте любой карточки пакет полностью откатывается.
- Карточки блокируются в стабильном порядке ID, чтобы снизить риск взаимных блокировок параллельных пакетов.
- Комментарий и статус согласования сохраняются в одной транзакции.
- Удалённые промо доступны в форме только для чтения до восстановления.
- Просроченные записи кэша фильтров удаляются автоматически.
- Добавлены модульные, race- и интеграционные тесты конфликтов и атомарности пакета.

### Бюджет OPEX по контракту в реестре сетей

- Новая вкладка карточки сети **«Инвестиции OPEX»**: пять статей договора
  (поддержание НТЗ/БДН, выкладка, предоставление отчётов, акция с фиксированной
  стоимостью, размещение карточки товара на сайте сети), ввод на квартал по брендам.
- Миграция `031_network_opex_budgets.sql`: `tbl_NetworkOpexBudgets` хранит бюджет
  помесячно, в двух базах НДС, со знаком. `CHECK (amount >= 0)` намеренно нет —
  возврат и корректировка вводятся отрицательной суммой.
- Квартальная сумма делится на три равные части до копейки, остаток от деления
  уходит в последний месяц квартала: итог квартала равен введённому, и помесячные
  значения не мельче копейки. Схема распределения плана здесь не применяется.
- Вводится сумма с НДС; базу «без НДС» считает сервер по ставке квартала и хранит
  рядом — колонка остаётся пригодной для сложения сетей с разными ставками.
- Оптимистичная блокировка на уровне квартальной ячейки: версией служит самая
  свежая из трёх её месячных строк, расхождение даёт `409`. Бюджет заводится
  только на бренд, у которого есть план года; снятие значения разрешено всегда.
- Витрина: бюджет вошёл в столбец «Инвестиции OPEX» карточки сети отдельной
  величиной (`registryOpexBudgetRub`) — в плане и в ожидаемом итоге. Факта у него
  нет и быть не может, в процентные инвестиции он не входит, чтобы не искажать
  эффективную ставку.

## Выполненные изменения (13.09.2026)

### Ступени контракта в реестре сетей — PR 1: схема и правило

- Миграция `032_network_plan_scales.sql`: `tbl_NetworkPlanScales` (ступень строки
  плана: порог, процент, пара «рубли / упаковки», расчётные колонки по прогнозу и
  факту), `tbl_NetworkPlanScaleSKU` (SKU на ступени: план, процент, крышка), крышка
  и итог правила на `tbl_NetworkPlans` (`cap_mode`, `cap_pct`, `forecast_scale`,
  `fact_scale`, `*_base_rub`), число ступеней в `tbl_NetworkPeriods.scales_count` и
  умолчания в `tbl_Networks`. Каждая существующая строка перенесена в ступень 1 с
  открытой крышкой.
- Правило (`services/network_scales.go`): достигнутая ступень — наивысшая, чей порог
  закрыт объёмом области; база к оплате — по каждому SKU от его плана: закрытая
  крышка → план, промежуточная ступень → объём, последняя открытая → объём,
  последняя процентная → min(объём, план × (1 + c%)). Пул на последней ступени
  режет крышкой и бренд с короткой лестницей. Плановые инвестиции считаются для
  каждой ступени, остаток к распределению — по каждой ступени.
- Проверка «числа не меняются»: в демо-контуре снимок 4 071 строки `tbl_NetworkPlans`
  до миграции и после пересчёта новым правилом совпал до копейки в обеих базах НДС.
- Пара «рубли / упаковки» плана (`services/network_plan_pairs.go`): вторая метрика
  считается по ценам контракта помесячно по схеме распределения и закрепляется после
  сохранения плана и после правки цен; без цены сохранённая пара не стирается.
- Интерфейс не менялся: клиент, не присылающий ступени, оставляет их как есть.
  Профиль, квартальный разрез, диалог SKU и годовой разрез — PR 2 и PR 3
  (`outputs/network-scales-proposal-v3.html`).

### Ступени контракта — PR 2: профиль, квартальный разрез, диалог SKU

- Профиль сети: блок «Ступени контракта» — число ступеней по умолчанию,
  поквартальные исключения (`scales_count`, в базе только исключение), крышка
  для новых строк. Сетка планов, присылая только НДС, исключения не стирает.
- «План и факт», квартал: строка бренда раскрывается в под-строки ступеней
  (порог с подписью шага у владельца, план с порогом пула у валового бренда,
  процент с наследованием снизу, «к выплате, если достигнута»), строка крышки
  владельца порога, лесенка (SVG), остаток к распределению по каждой ступени
  и «поровну» по ступени, чип SKU → диалог. Черновик формы v2
  (`network_plan_draft_v2`), пара «рубли / упаковки» по `entry_unit` бренда.
- Диалог «SKU бренда на ступени»: SKU из цен контракта плюс заведённые, ввод в
  единице бренда, наследование процента и крышки от бренда, остаток до плана,
  предупреждение «нет цены». «Заполнить по миксу» пока «поровну» — микс считает
  сервер, эндпоинт отложен в PR 3.
- Правило уточнено по живой проверке: закрытая крышка — `min(объём, план)`
  (иначе SKU с открытой крышкой плюс остаток бренда давали базу больше объёма);
  ступень без процента наследует процент ступени ниже (`effective_investments_pct`).
- Проверено в демо-контуре на сети 26 / Q2 2026: три ступени пула с крышкой
  +0,5 %, планы валовых брендов, закрытая крышка и SKU-исключение отдельного
  бренда — ввод, пересчёт черновика, сохранение, чтение назад; пробные данные
  сняты, инвестиционные колонки совпали с базовой линией.

### Ступени контракта — PR 3: год, прогноз, сводка, микс SKU

- «Прогноз» приведён к правилу ступеней: открытые месяцы берут долю квартального

  остаток бренда; подписи «ступень N», «база к оплате … · срез крышкой»,
  «порог не пройден». В контракт добавлены `forecast_scale`, `forecast_base_rub`,

### Рендер отчёта через HTML и headless Chromium (17.09.2026)
