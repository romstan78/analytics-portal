### 🚨 1. Критическая уязвимость: Mass Assignment (Перехват привилегий)

**Где:** `backend/handlers/promo.go` -> `SavePromo` (блок UPDATE)
**Суть:** Вы написали отличный код защиты от ручного изменения полей:
```go
if k != "id" && k != "deleted_at" && k != "updated_at" && k != "agreement1" && k != "agreement2" {
    existing[k] = v
}
```
**Угроза:** Вы добавили новые поля `agreement1_status`, `agreement1_comment`, `agreement2_status` в базу данных, но **забыли добавить их в этот фильтр**. 
*Что может сделать хакер (или хитрый менеджер)?* Он может перехватить POST-запрос к `/api/promo/save` и добавить в JSON тело: `{"agreement2_status": "approved"}`. Код слепо запишет это в `existing` и сохранит в БД. Менеджер 1 сможет согласовать промо за Менеджера 2 в обход всех проверок ролей из `ApprovePromo`.
**Как исправить прямо сейчас:**
Добавьте новые поля в черный список:
```go
if k != "id" && k != "deleted_at" && k != "updated_at" && 
   !strings.HasPrefix(k, "agreement") && k != "status" { ... }
```
*(А глобально — это повод быстрее перейти на DTO, см. пункт 3.1)*.

### 🚄 2. Нагрузка и Concurrency (Тест на 15 пользователей)

Система выдержит 15 пользователей, гонок данных (Race Conditions) в Go-коде нет (RateLimiter написан безопасно). Но есть потенциальный "затор" в базе данных.

**Узкое место: `GetPromoFilters` и Пул соединений**
*   **Как работает сейчас:** Вы используете `errgroup` и делаете **7 параллельных запросов** в базу для сбора списков (KAM, Бренд, Сеть и т.д.).
*   **Математика:** Если 4 менеджера одновременно зайдут на страницу "Анализ промо", бэкенд мгновенно запустит $4 \times 7 = 28$ параллельных SQL-запросов. 
*   **Проблема:** Ваш пул соединений (`DB.SetMaxOpenConns(25)`) ограничен 25 коннектами. 3 запроса встанут в очередь. При 15 пользователях (105 запросов) очередь станет заметной, интерфейс может "подвиснуть" на 1-2 секунды.
*   **Как улучшить:** Значения для фильтров (список брендов, сетей, механик) не меняются каждую секунду. **Их нужно кэшировать в памяти бэкенда** (например, с помощью пакета `github.com/patrickmn/go-cache`) на 5–10 минут. Это снизит нагрузку на БД при загрузке страницы до нуля.

**Узкое место: Экспорт CSV на фронтенде**
*   Кнопка "Экспорт" запрашивает `/api/promo/data?all=true` и скачивает *всё* в память браузера, после чего JS клеит строку `csv += ...`.
*   Если база разрастется до 50 000+ строк, вкладка браузера у пользователя "упадет" из-за нехватки памяти (Out of Memory).
*   **Как улучшить в будущем:** Генерация CSV должна происходить на бэкенде. Фронтенд должен скачивать готовый файл (Stream), а не JSON.

### 🧠 3. Архитектура и Технический долг (Что нужно доделать)

#### 3.1. Завершить избавление от `map[string]interface{}`
Сейчас в `SavePromo` происходит страшный "тяни-толкай": JSON мапится в `map`, потом конвертируется в `PromoInputDTO`, сервис это обогащает, возвращает `CalculatedFields`, который снова конвертируется в `map` и летит в БД. 
Это съедает процессорное время, лишает вас строгой типизации и порождает уязвимости (см. п.1).
*Что делать:* Полностью переписать функцию `UpdatePromo` и `InsertPromo` в `promo_repo.go`. Они должны принимать на вход структуру `PromoRow` или `PromoInputDTO`, а не мапу.

#### 3.2. Проблема потери точности (Float vs Decimal)
Все финансовые поля (рубли) у вас заданы как `float64` в Go. База данных, скорее всего, тоже использует `FLOAT`.
В финансовых системах это грозит багами плавающей запятой (например, `10.1 + 0.2` в JS и Go даст `10.300000000000001`). Для аналитики это терпимо, но если цифры пойдут в бухгалтерию — будут расхождения в копейках.
*Рекомендация:* При возможности переведите денежные колонки в БД на тип `DECIMAL(18,2)`.

#### 3.3. Отзыв Refresh Token (Угроза кражи сессии)
Сейчас `RefreshToken` живет в httpOnly куке 7 дней. Это безопасно против XSS атак. 
Но если ноутбук менеджера украдут, вы не сможете "выкинуть" его из системы. Бэкенд только генерирует токены, но не хранит выданные Refresh токены в БД.
*Рекомендация:* Создайте таблицу `tbl_RefreshTokens` (user_id, token_hash, expires_at). При логауте или смене пароля удаляйте их.
