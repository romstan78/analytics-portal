# Аудит архитектуры и безопасности проекта "Аналитический портал"
**Дата аудита:** 03.08.2026
**Статус проекта:** Enterprise-ready (стадия стабилизации)

## Резюме
Проект демонстрирует высокий уровень инженерной зрелости. Переход на 4-слойную архитектуру (Handlers -> Services -> Repository -> DB), использование DTO (`PromoRowDB`), внедрение `React Query` (TanStack) и реализация `Optimistic Locking` — это отличные решения. База кода готова к масштабированию.

Однако при переходе со свободных типов (map/JSON) на строгие (struct/DTO) возник ряд краевых эффектов, которые могут повлиять на целостность данных и бизнес-процессы.

## 🚨 1. Критические проблемы целостности данных (Data Integrity)

### 1.1. Проблема потери "Нуля" (`0` vs `NULL`)
В финансовой аналитике `NULL` (нет данных/промо не началось) и `0` (факт продаж равен нулю) — это принципиально разные значения. Текущая реализация стирает эту разницу.

*   **Фронтенд (`usePromoForm.ts`):** 
    Конструкция `parseFloat(form.actual_promo_sales_units) || null` при вводе `0` превратит его в `null` (т.к. 0 в JS — это falsy значение).
    **Решение:**
    ```typescript
    actual_promo_sales_units: form.actual_promo_sales_units !== '' && !isNaN(Number(form.actual_promo_sales_units)) 
      ? parseFloat(form.actual_promo_sales_units) 
      : null,
    ```
*   **Бэкенд (`models/PromoRowDB`):**
    Тип `float64` в Go по умолчанию равен `0.0`. Если фронтенд пришлет `null`, Go инициализирует его нулем и запишет `0.0` в базу данных.
    **Решение:** Перевести все опциональные/nullable числовые поля в `PromoRowDB` и `PromoInputDTO` на указатели:
    ```go
    ActualPromoSalesUnits *float64 `json:"actual_promo_sales_units"`
    ```
    *(Потребует адаптации функций маппинга в `promo_service.go`)*.

## 🚨 2. Логика блока "Согласование" (Уязвимость пагинации)

Текущая реализация перекрёстной фильтрации в `PromoApproval.jsx` содержит архитектурный разрыв между клиентом и сервером.

### 2.1. Скрытая потеря данных при клиентской фильтрации
*   **Проблема:** Метод `GetApprovals` возвращает `TOP 500` записей из БД (фильтруя только по KAM, году и месяцу). Затем фронтенд *в памяти* отсекает лишние Сети и Бренды (`filtered = filtered.filter(a => a.network_name === appliedNetwork)`).
*   **Угроза:** Если у KAM'а 600 промо на согласовании, а нужные бренды находятся с 501 по 600 позицию, бэкенд их не отдаст, а клиентский фильтр покажет пустой экран.
*   **Решение:** Внедрить фильтры `network_name`, `brand_as` и `mechanics` напрямую в SQL-запрос `GetApprovals` в `promo_repo.go`. Удалить фильтрацию из памяти фронтенда.

### 2.2. Заблокированная перекрёстная фильтрация
*   **Проблема:** В `PromoApproval.jsx` фронт перестал слать параметры в `getApprovalFilters`, чтобы не фильтровать "самих себя". 
*   **Решение:** На бэкенде переписать `GetApprovalFilters` по аналогии с `GetPromoFilters` (использовать `errgroup` и паттерн *exclude current column* для уникальных значений). После этого фронтенд должен снова начать слать все параметры.

## ⚠️ 3. Бизнес-процессы и Безопасность (Корректировка промо)

В реальном бизнесе согласующие (`agreement1`, `agreement2`) должны иметь возможность корректировать параметры промо-акции, если автор (KAM) недоступен. Но это порождает риск неконтролируемых изменений.

### 3.1. Защита от "случайного клика" (Фронтенд)
Для ролей согласующих нажатие кнопки "Сохранить" в `PromoEditDialog.jsx` должно сопровождаться подтверждением.
**Решение:** Добавить модальное окно:
*Текст:* "Вы вносите изменения в параметры промо-акции в роли согласующего. Вы уверены, что хотите сохранить изменения?"

### 3.2. Внедрение Audit Trail (Бэкенд)
Сейчас бэкенд в `SavePromo` пишет в логи `"user": "system"`. Если согласующий поменяет план продаж, концы будет не найти.
**Решение:**
Извлекать реальный логин пользователя из JWT-контекста и логировать его:
```go
usernameVal, _ := c.Get("username")
config.Logger.Info("promo_updated",
    "id", idInt,
    "user", fmt.Sprint(usernameVal), // <-- Реальный логин
    "timestamp", time.Now().Format(time.RFC3339),
)
```

### 3.3. Optimistic Locking и точность MSSQL
В `UpdatePromo` происходит строгое строковое сравнение: `WHERE updated_at = ?`.
**Угроза:** MSSQL `DATETIME` имеет точность 3.33 мс. Формат `time.RFC3339` или `121` из Go может не совпасть с реальным байтовым представлением в базе, вызывая ложные ошибки `409 Conflict`.
**Решение:** Если начнутся ложные срабатывания, переведите сравнение на уровне БД: `WHERE CONVERT(NVARCHAR, updated_at, 121) = ?`.

## ⚙️ 4. Производительность и Архитектура

1.  **Кэширование (`FiltersCache`):** 
    Добавление in-memory кэша на 5 минут для `GetPromoFilters` — блестящее решение, спасающее пул соединений MSSQL (т.к. используется 7 горутин на каждый запрос).
    *Заметка на будущее:* Если появится Row-Level Security (RLS) и фильтры станут зависеть от роли пользователя, ключ кэша нужно будет дополнить идентификатором роли/юзера: `cacheKey := "filters:" + role + ":" + ...`
2.  **Mass Assignment:** 
    Функция `applyJSONToRow` содержит жесткий blacklist (`if k == "id" || strings.HasPrefix(k, "agreement") ...`). Это отличная защита от попыток передать статус согласования через эндпоинт сохранения.
3.  **Экспорт в CSV (Угроза памяти):**
    При росте базы до 50 000+ записей, загрузка `?all=true` в оперативную память браузера вызовет краш (Out of Memory).
    *Заметка на будущее:* Перенести генерацию CSV на бэкенд (streaming) и скачивать готовый `.csv` файл.
